## CLI 自判(主人原话 2026-11-10)

主人原话:「关于插件cli的问题,每个pr都要自己判断需不需要更新cli,不单单针对你,针对所有cindy」

- 每个 PR 提 PR 者自己判断要不要同步 CLI(`lib/agent-cli.mjs`),并把结论写进 PR 描述:要么「已更新 CLI:改了哪几条命令」,要么「不需要动 CLI:理由 X」,不得省略。
- 判断口径:CLI 的目标是「不开网页也能把整套操作做完」。凡新增/改动 `lib/server.mjs` 的 `/api/*` 路由、参数形状或语义——尤其账号(导入/备注/删除/续期托管)、出口(改绑/检查)、代理(增删/探测)、市场安装、报 issue 这类能纯命令行完成的动作——就要检查 CLI 有无对应子命令;纯内部实现(扫描器、渲染、图标、测试)一般不用。
- 合并方在合并检查清单里核对这条,未填退回补齐。规则也写进 `AGENTS.md` 与 `docs/releasing.md`。
- 背景:CLI 曾长期落后服务端(导入账号 PR #64、改出口 0.1.95 一度只能开网页点,直到 PR #73 补齐 12 条路由)。`clean-login help` 看全。

## 前端语法护栏

- 把前端 JS 当文本读并断言子串,发现不了语法错误;全量测试全绿也不能证明入口脚本可解析。多语言字典批量编辑容易引入多余逗号。
- 提交前必须让入口脚本及其引用文件通过真实解析/语法检查;检查 HTML 引用的脚本文件真实存在。护栏本身也要做破坏性验证(故意引入一处语法错误确认会报错,再还原)。

## 登录入口必须有

- 任何涉及浏览器登录的供应商都必须提供登录入口,不接受机制解释代替交付。
- 入口判定不能只绑「已安装插件暴露 runnable oauth 方法」;magpie 原生供应商(antigravity/codex/grok 这类无 plugin: 前缀)由 magpie 本体做 OAuth,永远扫不到插件方法。正确判据是「该供应商需要登录」(registry 的 signInMode),不是「有没有插件方法」。
- 遇到某供应商没入口,按类别排查补齐,不逐个反复来回。

## 卡片文案

- 供应商卡片只陈述可核实事实(如是否找到浏览器登录方式);不得声称「尚未验证 / not verified」或暗示插件掌握验证状态——插件没有通道得知一次登录尝试的最终结果。
- 可邀请用户直接尝试并承诺失败时如实报错。
